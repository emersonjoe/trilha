# Public API and deprecation policy

> 🇺🇸 English · [🇧🇷 Português](docs/pt-BR/API.md)

This document draws the line between what the framework promises and what it merely happens to
expose today. Anything on the promised side changes under the policy below; anything on the
other side can change in any release, without notice.

## What is covered

The exported symbols of these packages, with the behaviour their documentation describes:

| Package | What it is |
|---|---|
| `github.com/emersonjoe/trilha` | the runtime: `App`, `Config`, `Ctx`, `Route`, errors, test client |
| `.../h` | the HTML DSL: `Node`, elements, attributes, `Render` |
| `.../ui` | the component kit built on `h` |
| `.../tmpl` | `html/template` inside a page |
| `.../ai` | the model client and the agent loop |
| `.../ai/mcp` | the MCP server and client |
| `.../auth` | OpenID Connect: `Provider`, `Config`, `Store`, the ready-made handlers |
| `.../cache` | the cache interface and the in-memory implementation |

The full list of symbols lives in [`api/current.txt`](api/current.txt), one line per symbol,
generated from the source.

## What is not covered

- Everything under `internal/`. The Go compiler already enforces it; it is stated here so no
  one goes looking for a way around.
- The `cmd/trilha` binary: the commands and their flags are documented and stable in practice,
  but the exact output — text, column order, exit codes beyond `0`/`1` — is not a contract.
- The content of the generated `trilha_gen.go`. It is regenerated by the tool that wrote it.
- The HTML that `ui` produces: classes, element order and structure change as the kit evolves.
  What is promised is the function signature and what the component is for, not its markup.
- The `site/` and `examples/` packages. They are applications that live in the repository, not
  a library.
- Anything whose documentation calls it experimental.

## What counts as a breaking change

- Removing or renaming an exported symbol.
- Changing a function or method signature, including the type of a parameter or result.
- Removing a field from an exported struct, or changing its type.
- Adding a method to an interface the caller is expected to implement.
- Narrowing what a function accepts, or weakening what it guarantees, even with the signature
  untouched — a `Config` field that starts being required, an error where there used to be a
  zero value.

**Not** a breaking change: adding a function, a method, a struct field or a constant. Because
of that, fill configuration structs by field name (`trilha.Config{Env: trilha.Prod}`), never
positionally — a new field would break the positional form and it is not meant to.

## Deprecation policy

Before a covered symbol disappears:

1. Its doc comment gains a `Deprecated:` paragraph saying what to use instead.
2. `CHANGELOG.md` lists it under `Deprecated`, in the release where the mark appears.
3. It keeps working for **at least one minor version** alongside the replacement.

```go
// Sign returns the signed value of v.
//
// Deprecated: use Signer.Sign, which takes the expiry explicitly.
func Sign(v string) string { … }
```

The only exception is a security fix that cannot be made compatible. When that happens, the
CHANGELOG says so in those words, and the release notes explain the migration.

While the project is at `0.x`, a breaking change may land in a minor version — `0.24 → 0.25` —
as `GOVERNANCE.md` already states. The policy above still applies: the deprecation cycle is
what turns "may break" into "will have been announced".

After `1.0`, breaking changes only happen in a major version, and a deprecated symbol survives
until the next major.

## How the line is enforced

`api/current.txt` is generated from the source and versioned. A test compares it on every run:

```bash
make test   # fails if the exported surface differs from the file
make api    # rewrites the file, after an intentional change
```

The failure lists what came in and what went out. Whoever reviews the change sees the removed
line in the diff — which is the whole point, since removing a field from a struct is otherwise
one line that compiles fine on this side of the fence.

A symbol carrying `Deprecated:` shows up marked in the file, so the review also sees when
something enters deprecation, and when something leaves without having gone through it.

**What the test does not catch**: behaviour. A function that keeps its signature and starts
returning something else passes the check. That is what the CHANGELOG and the tests of each
feature are for; the surface file guards the compilation, not the semantics.
